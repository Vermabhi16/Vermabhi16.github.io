Kafka Spark Streaming Delta Lake E-commerce Platform

Real-Time Streaming Analytics

Built a real-time streaming analytics platform for a major e-commerce company processing 1 million events per second. The platform enables real-time personalization, fraud detection, inventory updates, and customer journey analytics with sub-second latency.

01 Business Challenge

The e-commerce platform needed real-time capabilities to compete with market leaders and improve customer experience:

  • Batch processing with 4-hour delays preventing real-time personalization
  • Fraud detection happening post-transaction, resulting in $10M+ annual losses
  • Inventory counts updated hourly, causing overselling and customer disappointment
  • No real-time visibility into customer journey for marketing optimization
  • Peak traffic during sales events overwhelming batch infrastructure
  • Inability to react to trends and anomalies in real-time

02 Solution Architecture

Implemented a kappa architecture using Apache Kafka as the central event backbone, Spark Structured Streaming for processing, and Delta Lake for the unified batch and streaming data store.

03 Technical Implementation

Spark Structured Streaming

// PySpark - Real-time Session Analytics 
from pyspark.sql.functions import *
from pyspark.sql.types import *

# Read from Kafka
clickstream = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", kafka_brokers)
    .option("subscribe", "clickstream")
    .option("startingOffsets", "latest")
    .option("maxOffsetsPerTrigger", 100000)
    .load()
    .select(
        from_json(col("value").cast("string"), event_schema).alias("event"),
        col("timestamp").alias("kafka_timestamp")
    )
    .select("event.*", "kafka_timestamp"))

# Session window aggregation
sessions = (clickstream
    .withWatermark("event_time", "30 minutes")
    .groupBy(
        session_window("event_time", "30 minutes"),
        "user_id",
        "device_type"
    )
    .agg(
        count("*").alias("event_count"),
        countDistinct("page_url").alias("unique_pages"),
        sum(when(col("event_type") == "purchase", col("amount")).otherwise(0)).alias("revenue"),
        collect_list("event_type").alias("event_sequence"),
        first("event_time").alias("session_start"),
        last("event_time").alias("session_end")
    )
    .withColumn("session_duration_sec",
        unix_timestamp("session_end") - unix_timestamp("session_start")
    ))

# Write to Delta Lake
(sessions.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/checkpoints/sessions")
    .trigger(processingTime="10 seconds")
    .toTable("gold.user_sessions"))

Fraud Detection Pipeline

// Real-time Fraud Scoring with ML 
from pyspark.ml import PipelineModel
import mlflow

# Load production fraud model
fraud_model = mlflow.spark.load_model("models:/fraud_detection/Production")

# Feature engineering on stream
transactions = (spark.readStream
    .format("kafka")
    .option("subscribe", "orders")
    .load()
    .select(from_json(col("value").cast("string"), order_schema).alias("order"))
    .select("order.*"))

# Enrich with historical features from feature store
user_features = spark.table("feature_store.user_features")
enriched = transactions.join(
    broadcast(user_features),
    "user_id",
    "left"
)

# Score in real-time
scored = fraud_model.transform(enriched)

# Route high-risk transactions
(scored
    .filter(col("fraud_probability") > 0.8)
    .writeStream
    .format("kafka")
    .option("topic", "high-risk-transactions")
    .option("checkpointLocation", "/checkpoints/fraud")
    .trigger(processingTime="1 second")
    .start())

# Store all scores for analysis
(scored
    .writeStream
    .format("delta")
    .option("checkpointLocation", "/checkpoints/fraud-scores")
    .toTable("gold.transaction_fraud_scores"))

06 Key Learnings

  • Kafka partition count significantly impacts parallelism - plan for growth
  • Watermarks and late data handling require careful business requirement analysis
  • Delta Lake's streaming support enables true lakehouse with minimal complexity
  • Feature store is essential for consistent ML scoring in real-time
  • Schema evolution in streaming requires strict compatibility policies
